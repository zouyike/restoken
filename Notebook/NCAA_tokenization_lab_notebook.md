Proposed ICLR experiment - **representation-controlled fine-tuning** (PLAN ONLY, not started, awaiting Yike's decision):
- Rationale: every headline number in the paper is zero-shot prompting of frozen models, so at a representation-learning venue the contribution reads as a curated vocabulary plus prompt engineering plus a benchmark. Fine-tuning turns "ResToken is a good *interface*" into the testable claim "ResToken is a good *learning target*".
- Design: one base model, three arms differing **only** in the target string for the identical molecule - ResToken vs HELM vs SMILES. Same molecules, same instruction, same tokens-seen budget, same LoRA config, same decoding. Crossed with corpus size 0 / 100 / 1k / 10k to give a sample-efficiency curve; 12 LoRA runs.
- Data is free and needs no experiment: `CyclicPeptideAssembler` deterministically maps any token sequence to SMILES (already validated on 8,130 molecules), so a paired three-representation corpus of ~50k length 5-8 sequences can be minted on CPU, labelled by RDKit.
- **Anti-circularity rule, mandatory**: train only on rule-computable labels (the 7 validator constraints - charge, HBD, HBA, rotatable bonds, N-Me count, length, backbone adjacency). The permeability judge must never enter the training signal, so predicted permeability stays an out-of-sample generalisation test.
- **Anti-memorisation rule, mandatory**: report constraint satisfaction on held-out constraint *profiles* never trained on, plus novelty (fraction of generations absent from the training corpus) and diversity, otherwise high validity is trivially explained by memorising validator-passing strings.
- Compute: Qwen3.5-9B or Gemma-3-12B (both already in the paper), LoRA bf16 on gpu_cpu 4090D 48 GB; envs `ai`, `gemma3_env`, `llama4` all carry torch+transformers+trl+peft+unsloth. Estimated ~8 GPU-hours plus eval - compute is not the constraint, harness time is.
- Honest prediction, both outcomes publishable: SMILES should improve sharply from its 18.1% zero-shot validity because fine-tuning fixes syntax, so the headline gap will shrink. If ResToken still leads, the claim is far stronger than the zero-shot one. If SMILES converges, the finding becomes "ResToken's advantage is a low-data / zero-shot advantage that supervision erases", which is a clean representation result with a scaling curve. Not sure which will happen - that is the point of running it.

### 2026-09-04 | CORRECTION: my experiment could not have shown ResToken beating HELM — and the plan that can

- **I have to correct the conclusion I wrote three entries up.** I did not compare ResToken against HELM. I compared two *spellings of the same encoding*, and the tie was guaranteed before a single GPU hour was spent. Evidence, from the corpora the models actually trained on:
  - ResToken target: `Sequence: e06-A59-A159-N27-A170-A83-E10`
  - HELM target: `Sequence: PEPTIDE1{[e06].[A59].[A159].[N27].[A170].[A83].[E10]}$PEPTIDE1,PEPTIDE1,1:R1-7:R2$$$V2.0`
  Same seven block IDs, same order, same cyclization semantics. The only difference is punctuation and a wrapper. **Informationally identical**, so "ResToken 0.98 vs HELM 0.99" is close to a tautology, not a finding.
- **Worse: the mechanism of ResToken was absent from the experiment entirely.** The prompt input was only the target metrics; it contained **no block dictionary**. ResToken's whole claim is that each token carries eight designable semantic properties (`class`, `chirality`, `charge_label`, `mc_type`, `mc_nmod`, `mc_len`, `sc_bulk`, `polarity_bin`, `flex_bin`) while hiding structure. In the paper's zero-shot setting that dictionary IS injected into the prompt, which is precisely why ResToken wins there. In my fine-tune the model never saw a single property - it saw opaque IDs, exactly like HELM. I ablated away the independent variable and then measured its effect.
- **Third reason a win was impossible: there was no pressure to use semantics.** 399 of 400 blocks appear in even the n=1000 corpus, each at least 123 times. The model can memorise the ID vocabulary outright. A representation that helps you *compose* an unseen block earns nothing when every block is seen a hundred times.
- **What survives from the completed grid**: the SMILES comparison is still valid and still interesting (0.16 -> 0.78 -> 0.99 mean validity; supervision repairs SMILES syntax), and the harness, corpus builder, eval and figure pipeline are all built and verified. The ResToken-vs-HELM row should be reported as a **null by construction** and used as the motivation for the real experiment, not as a result.

Plan to actually test the claim, in dependency order. Nothing launched.
- **E1 - surface the semantics (prerequisite for everything else).** Emit compositional tokens whose properties are visible in the string the model reads and writes, e.g. `<I|L|neu|alpha|std|large|low|med>` in place of `A01`, with a deterministic decoder back to the block ID. Add it as a **fourth arm**, `restoken_semantic`, alongsideid-ResToken, HELM and SMILES so the ID-vs-semantic contrast is measured inside one grid. Corpus builder already emits all arms from one molecule set, so this is one function.
- **E2 - HELD-OUT BLOCK GENERALISATION. This is the experiment that can win, and the only one where HELM must lose by construction.** Split the 400 blocks 320 train / 80 held out. Train only on molecules built from the 320; evaluate on prompts whose target requires held-out blocks. An opaque ID (`[A159]`, or `A159`) that never appeared in training cannot be produced correctly - the model can only hallucinate a seen ID. A semantic token can be *composed* from its property description. If `restoken_semantic` recovers held-out blocks at a materially higher rate than HELM, that is a genuine representation advantage rather than an interface one, and it is the claim the paper wants. Predicted, and this is a real prediction and not a hedge: HELM and id-ResToken near 0 on held-out blocks, `restoken_semantic` materially above 0. If it comes out flat, ResToken genuinely is HELM with nicer syntax and the manuscript should claim interface only.
- **E3 - fix the constraint metric, then re-test conditioning.** Per-field tolerance bands instead of seven-field exact match; the current metric produced max 0.010 across 30 cells, i.e. no signal at all. Property-conditioned generation is where surfaced semantics should pay off, and right now it is unmeasurable.
- **E4 - library extension without retraining.** Add new NCAA blocks after training and test whether the semantic form can address them from description alone. This answers the paper's own stated Limitation ("new NCAAs require manual addition") and is the version of the claim that matters most for the group's actual pipeline work.
- Cheaper intermediate worth one arm: **id-ResToken with the dictionary injected into the fine-tune prompt**, which is closer to what the paper actually does. It partly reintroduces the prompt cost that ResToken exists to avoid, so it is a control rather than a product.
- **Not sure, stated plainly**: E2 is a real test with a real chance of a null. I am not confident it wins. But it is the first version of this experiment that *could* win, which the completed grid could not.

### 2026-09-04 | E1+E2+E3 LAUNCHED — the experiment that can actually separate ResToken from HELM

- Built and launched. **Jobs 390474-390482**, 3 arms x 3 models (Qwen2.5-0.5B, Llama-3.1-8B, Qwen3.5-9B), n=10,000 train corpus, all pinned `-p gpu_cpu` after the OOM lesson.

  - `restoken_id` -> `N04-N04-A71-Q02-A36-N48` (what the old grid actually tested)
  - `restoken_semantic` -> `<I|D|neu|beta|NO|mid|small|low|low>-...` (all 9 properties on the surface)
  - `helm` -> `PEPTIDE1{[N04].[N04]...}$...$$$V2.0`
- **Anti-tautology guard, which the design needed.** The prompt gives only **4 of the 9** fields, so copying the spec into the answer is not a sufficient response - the model must complete the remaining 5 into a combination that actually exists in the 400-block library. Without this the semantic arm would win by definition.
- **E2, the held-out split, and it came out clean.** Blocks are partitioned by their full 9-field property tuple and whole tuple classes are held out: **322 train / 78 held out, verified ZERO property-tuple leakage.** Critically, every individual property *value* present in held-out blocks is also present in training (checked field by field: no unseen values), so a held-out block is composable from parts but not retrievable by ID. This is compositional generalisation in the strict sense.
  - A random 320/80 block split would NOT have worked: measured over 200 random splits, the best left only 35 of 80 held-out blocks genuinely unreachable. Partitioning by tuple class is what makes the test sharp.
- Eval corpus: 2,000 items, **1,213 of them contain a spec satisfiable only by a held-out block**, drawn from 25 held-out-only 4-field spec classes; the other 19 shared spec classes serve as control prompts. The evaluator balances held-out against control 50/50 so both numbers have support.
- **Headline metric `spec_match_heldout`**: on a prompt whose 4-field spec can only be satisfied by a held-out block, did the arm emit a residue with those properties AND does that residue exist in the library? `restoken_id` and `helm` must produce an identifier never seen in training, so they can only guess. `restoken_semantic` can compose. `spec_match_seen` on control prompts is the sanity baseline - an arm that fails the seen case makes its held-out number meaningless.
- **A design fact worth reporting regardless of the outcome: ResToken's LLM-facing semantics are LOSSY.** Only **175 distinct 9-field property tuples cover all 400 blocks**, and just **89 blocks (22%) are uniquely identified by their properties** (multiplicity up to 26). So the semantic form cannot decode to a unique block ID in 78% of cases. That is why scoring is property-satisfaction rather than ID-recall, and it is an honest limitation of the representation that the manuscript does not currently state.
